# Инженерные уроки ScreenPilot

## Как читать этот документ

Это не описание архитектуры и не отчёт о готовности MVP. Здесь собраны только инженерные уроки, которые подтверждаются кодом, ADR, тестами, аппаратным чек-листом и Git-историей на момент анализа.

История короткая: 11 содержательных коммитов от 5 до 21 августа 2026 года. В ней нет `git revert` и нет отдельных веток с альтернативными реализациями. Поэтому выводы ниже не приписывают проекту незафиксированные причины: там, где событие описано в ADR или чек-листе, но не выделено отдельным коммитом, это сказано явно.

Незакоммиченные изменения, относящиеся к AppFleet/Inno Setup и переносу пользовательских данных, рассмотрены как незавершённая работа. Они не считаются подтверждённым рабочим решением, пока не пройдут чистую установку, обновление и удаление.

## Проблема: JNA-описание Windows DisplayConfig metadata было неверным

**Уверенность: высокая.** 16.09.2026 ошибка воспроизведена статически по SDK и исправлена; exact-size/offset unit-тесты и read-only probe активного встроенного экрана прошли. Проверка исправления на внешнем HDMI-target пока `NOT TESTED`.

### Что происходило

`QueryDisplayConfig` успешно возвращал internal и HDMI paths, включая target ID, тип подключения и рациональную частоту 59,940 Гц. Старый JNA-код передавал `DISPLAYCONFIG_DEVICE_INFO_HEADER` в неверном порядке и выделял для `DISPLAYCONFIG_TARGET_PREFERRED_MODE` лишь 40 байт вместо 80. Из-за этого metadata нельзя было считать достоверно прочитанной.

### Корневая причина

Причина была в JNA layout: SDK задаёт порядок header как `type`, `size`, `adapterId`, `id`, а preferred mode содержит полный вложенный `DISPLAYCONFIG_TARGET_MODE`. Старый независимый P/Invoke smoke не сохранил точное описание/байты и мог повторять эту же ошибку, поэтому не исключал её.

### Что делали или пробовали

Рассматривались три пути:

- считать отказ metadata фатальным;
- заменить Display Configuration API реестром, WMI или сторонней библиотекой;
- оставить Display Configuration API источником paths и добавить ограниченный read-only fallback через GDI.

В `6163100` добавлены `WindowsDisplayDiscovery`, retry при `ERROR_INSUFFICIENT_BUFFER`, GDI fallback и `GdiMappingConfidence`. Позднее declaration исправлена: размеры и offsets native-пакетов закреплены тестами, а успешный metadata API имеет приоритет над fallback. Отказ от API или подмена его WMI/реестром не применялись.

### Рабочее решение

Для каждого target код сначала запрашивает все предусмотренные metadata через Display Configuration API. При ошибке он сохраняет достоверные поля из `DISPLAYCONFIG_PATH_INFO`, а `EnumDisplayDevicesW` и `EnumDisplaySettingsExW` использует только для безопасного имени, диагностики GDI, bounds и списка режимов. У результата есть явная степень связи: `AUTHORITATIVE`, `FALLBACK` или `UNAVAILABLE`.

### Почему решение сработало

Оно не смешивает данные разной надёжности: сведения из корректно прочитанного API не заменяются эвристикой, а недоступные поля не выдумываются. Последующий опасный сценарий может запретить автоматическое действие, если связь с физическим target имеет лишь `FALLBACK`.

### Как можно было обнаружить проблему раньше

До hardware smoke нужны exact-size/offset тесты для каждой JNA-структуры и её вложенных полей. Затем минимальный read-only smoke на целевом драйвере должен вызывать все variants `DisplayConfigGetDeviceInfo`, фиксировать Win32-коды и сверять сомнительный результат с независимым probe, чья native-декларация и сырые байты доступны для проверки. Одного `QueryDisplayConfig` недостаточно.

### Как предотвратить повторение

- Сверять JNA field order, offsets, выравнивание и размер полного вложенного пакета с Windows SDK.
- Тестировать не только успешный API-вызов, но и частичную доступность зависимых API.
- Хранить источник и уровень уверенности каждого поля модели оборудования.
- Не разрешать потенциально опасную автоматизацию по fallback-идентификатору.
- Оставлять fallback read-only, пока его связь с физическим устройством не подтверждена.

### Область применимости

- Windows desktop;
- Java/JNA и другие FFI;
- интеграция с SDK и драйверами;
- тестирование native-контрактов.

### Потенциальный reusable lesson

1. FFI-структуру нельзя считать проверенной только по её общему размеру: критичны порядок, offsets, вложенность и alignment.
2. Независимый probe полезен лишь когда его native-декларация и результат проверяемы, а не повторяют исходную ошибку.
3. Частичный отказ системного API — штатный режим, но только после доказательства корректности native-контракта.

## Проблема: блокирующий named pipe терял ответ на первой подписке mpv

**Уверенность: высокая.** Реальный симптом и причина зафиксированы в ADR-0003; код предыдущего коммита содержал синхронный `RandomAccessFile`, а `3bdd55f` заменил его на долгоживущий overlapped-клиент.

### Что происходило

При первом `observe_property` mpv не присылал ожидаемый ответ. Клиент одновременно должен был постоянно читать события mpv и отправлять новые JSON-команды через один Windows named pipe. Блокирующее чтение не позволяло надёжно записать команду, пока другой поток ждёт событие.

### Корневая причина

Первоначальный spike использовал синхронный `RandomAccessFile` и модель «записать команду, затем прочитать ответ». Она подходит только для простого request/response. JSON IPC mpv смешивает ответы и unsolicited events, а Windows-клиенту нужна одновременная операция чтения и записи с overlapped I/O.

### Что делали или пробовали

Рассматривались:

- синхронный путь без постоянного чтения событий;
- два разных pipe-соединения — для команд и событий;
- один pipe с overlapped I/O для каждой операции.

Первый подход фактически не прошёл реальный прогон. Второй не был выбран. В том же крупном коммите `3bdd55f` исходный синхронный клиент заменён production-вариантом; отдельного промежуточного commit с неудачной реализацией нет.

### Рабочее решение

`MpvIpcClient` открывает pipe с `FILE_FLAG_OVERLAPPED`, запускает единственный постоянный reader и создаёт отдельные `OVERLAPPED` с event handle для каждой native read/write-операции. Ответы коррелируются монотонным `request_id` в `ConcurrentHashMap`, а события доставляются независимым слушателям. У обычных команд есть тайм-аут 3 секунды, у загрузки — 15 секунд; разрыв pipe переводится в контролируемую ошибку.

### Почему решение сработало

Ни один поток не «владеет» потоком сообщений по принципу «запросивший читает свой ответ». Единственный reader разбирает каждую строку ровно один раз и маршрутизирует её либо ожидающему запросу, либо обработчикам событий. JNA `Memory` удерживается до завершения native I/O, поэтому Windows не получает ссылку на уже освобождённый Java-буфер.

### Как можно было обнаружить проблему раньше

Нужен интеграционный тест, который до ответа на команду генерирует событие и параллельно отправляет вторую команду. Полезна также проверка закрытия pipe при незавершённом чтении и при тайм-ауте.

### Как предотвратить повторение

- До выбора транспорта описывать, кто и как читает сообщения, ответы и события.
- Не применять синхронный request/response-клиент к протоколу с асинхронными событиями без доказательства его корректности.
- Для native asynchronous I/O фиксировать владение handle, буфером, callback и операцией отмены.
- Добавлять тесты на out-of-order responses, events между командами, timeout и disconnect.

### Область применимости

- Windows desktop;
- Java / Spring;
- локальная сеть;
- API / HTTP;
- состояние приложения;
- тестирование;
- любой программный проект.

### Потенциальный reusable lesson

1. Один канал с событиями требует единственного reader и явной диспетчеризации сообщений.
2. Корреляция запросов нужна даже для локального IPC.
3. У асинхронной native-операции должны быть явные владельцы буфера, handle и отмены.

## Проблема: target в clone или inactive-состоянии не имеет GDI-режима

**Уверенность: высокая.** Через 11 минут после начального прототипа мутации появился commit `09ba831` «Support inactive display recovery snapshots» с корректировкой mutator, smoke-команд и тестов; сценарий clone дополнительно подтверждён аппаратным чек-листом.

### Что происходило

Начальная реализация ожидала, что выбранный внешний экран уже активен как независимый desktop, имеет `\\.\DISPLAYn`, текущий `DEVMODEW` и режим. В clone target не имел отдельного GDI-имени и режима. Значит, он не мог быть прямым аргументом для смены режима и не мог проверяться при rollback так же, как active target.

### Корневая причина

В модели были смешаны два разных состояния: физический доступный target и его временная проекция в активный GDI desktop. Второе отсутствует, пока Windows не переведёт topology в Extend. Предположение «у выбранного target всегда есть GDI mode» оказалось неверным.

### Что делали или пробовали

Первый `display-mutation recovery prototype` из `bb095ed` выбирал только активный внешний display и сохранял его GDI-имя и режим в snapshot. Затем `09ba831` перестроил поток:

- target можно выбрать как available, даже если он не independent active;
- snapshot сохраняет topology и modes всех активных source, но у исходного target допускает отсутствие GDI-имени и режима;
- после `SetDisplayConfig(...EXTEND)` target заново ищется по `adapter LUID + target ID`;
- режим меняется лишь после появления отдельного active source;
- rollback неактивного исходного target проверяется по fingerprint topology.

Подход «сразу применить `DEVMODEW` к исходному clone target» был отменён исправлением.

### Рабочее решение

Снимок создаётся до изменения topology, но не требует фиктивного `DEVMODEW` для inactive target. Подготовка Extend возвращает заново обнаруженный active target. Если Windows активировала не тот target или independent source не появился, операция останавливается и начинается rollback. Recovery journal закрывается только после подтверждённого восстановления.

### Почему решение сработало

Физическая идентичность target (`adapter LUID + target ID`) переживает смену topology лучше, чем временное GDI-имя. Код сравнивает состояние с тем свойством, которое реально существует до или после перехода, и не пытается восстановить несуществующий режим.

### Как можно было обнаружить проблему раньше

До реализации режима стоило составить матрицу topology: только ноутбук, Extend, Clone, неактивный внешний target, несколько внешних target. Для каждой строки нужно проверить, какие API-поля действительно доступны до и после перехода.

### Как предотвратить повторение

- Разделять постоянный идентификатор устройства и временный идентификатор его текущей проекции в ОС.
- Хранить snapshot на уровне topology, а не только на уровне «текущий режим выбранного окна».
- После изменяющей операции заново читать фактическое состояние, не использовать объекты, полученные до неё.
- Не продолжать, если ОС активировала ресурс, отличный от выбранного пользователем.

### Область применимости

- только этот проект;
- Windows desktop;
- состояние приложения;
- тестирование;
- любой программный проект.

### Потенциальный reusable lesson

1. Не путать идентичность ресурса с его текущим представлением в операционной системе.
2. После смены topology, прав, подключения или роли повторно обнаруживать ресурс по стабильному ID.
3. Отсутствующее в исходном состоянии поле не следует подменять вымышленным значением для rollback.

## Проблема: дробная частота 59,940 Гц терялась при переходе к `DEVMODEW`

**Уверенность: высокая для факта и решения; средняя для точной последовательности правок.** Аппаратный чек-лист прямо описывает первый smoke, rollback и изменение поведения, но Git не содержит отдельного коммита именно для этой корректировки.

### Что происходило

Read-only Display Configuration API корректно показал 59,940 Гц. При попытке передать этот режим через `DEVMODEW` драйвер принимал только 60 Гц. Первый безопасный smoke обнаружил несовпадение, а операция была отменена. Простое округление создавало риск сменить режим не на тот, который выбрал алгоритм.

### Корневая причина

Разные Win32 API выражают частоту с разной точностью: `DISPLAYCONFIG_PATH_INFO` даёт рациональную частоту, а используемое поле `DEVMODEW` — целочисленную. Это не ошибка вычисления FPS, а потеря представимости при переходе между API.

### Что делали или пробовали

Из требований и ранней модели уже следовало хранить rational refresh. Первый hardware smoke показал, что преобразовывать 59,940 к 60 для `ChangeDisplaySettingsExW` небезопасно. Проект отказался от округления, добавил проверку и оставил только режимы, явно подтверждённые драйвером. Датировать изменение точнее, чем интервал этапа 5, по истории нельзя.

### Рабочее решение

`DisplayMode` хранит рациональную частоту. Перед применением берётся только `DEVMODEW`, перечисленный драйвером; дробная частота не округляется и не конструируется вручную. Операция проходит `CDS_TEST`, затем временное применение и read-back с допуском ±0,02 Гц. При mismatch выполняется rollback.

### Почему решение сработало

Режим остаётся тем, что фактически поддерживает драйвер, а не тем, что приложение умеет приблизительно отобразить. Проверка после применения ловит и другие случаи, когда драйвер молча выбирает иной режим.

### Как можно было обнаружить проблему раньше

Нужны contract-тесты конвертации между всеми модельными и native-представлениями: 23,976; 29,970; 59,940; 60 и 120 Гц. Для каждого режима следует проверять не только форматирование, но и возможность lossless применить его целевым API.

### Как предотвратить повторение

- Не использовать `double` или округлённое UI-значение как источник для native-операции.
- Хранить точное значение до последней границы, где API его поддерживает.
- Применять только режимы, полученные от драйвера, и проверять фактический результат.
- Для необратимых или заметных изменений всегда иметь rollback после post-condition check.

### Область применимости

- Windows desktop;
- Java / Spring;
- UI;
- состояние приложения;
- тестирование;
- любой программный проект.

### Потенциальный reusable lesson

1. Формат отображения и формат применения — разные контракты.
2. Преобразование с потерей точности нельзя использовать для команды управления оборудованием.
3. Успешный API-вызов не заменяет проверку фактически применённого состояния.

## Проблема: после EOF следующий файл оставался на паузе

**Уверенность: высокая.** Симптом, исправление и регрессионный тест внесены в release-коммите `f8c89d8`; аппаратная перепроверка release build пока остаётся `NOT TESTED`.

### Что происходило

После EOF или возврата mpv в idle UI мог показывать готовое к воспроизведению состояние, но следующий файл не начинался без дополнительного нажатия Play. Система неявно полагалась на состояние `--keep-open=yes`.

### Корневая причина

После EOF mpv мог сохранить `pause=true`. Обычный путь `loadfile` не задавал желаемое состояние явно и интерпретировал неявный default плеера как контракт приложения.

### Что делали или пробовали

Первоначальный подход полагался на поведение mpv после загрузки файла. В commit `f8c89d8` он заменён явной командой `set_property pause false` для каждой обычной загрузки. Существующая ветка восстановления pause после software fallback сохранена отдельно.

### Рабочее решение

После `file-loaded` адаптер задаёт `pause=false` для обычной загрузки. Если это специальный путь восстановления после ошибки декодирования, он восстанавливает заранее сохранённое pause-состояние. Unit-тест дважды загружает файл после stop и проверяет два явных значения `false`.

### Почему решение сработало

Приложение владеет своим переходом состояния `LOADING → PLAYING`, а не зависит от исторического состояния внешнего процесса. Специальный сценарий fallback выражен отдельным условием, а не скрытым побочным эффектом.

### Как можно было обнаружить проблему раньше

Тесты lifecycle плеера должны покрывать не один `loadfile`, а последовательность `load → EOF/stop → load`, включая auto-next плейлиста, смену трека и software fallback. Нужна проверка наблюдаемого состояния плеера, не только факта отправки load-команды.

### Как предотвратить повторение

- После каждой границы с внешним процессом явно задавать желаемое состояние.
- Не считать значение по умолчанию стабильным после EOF, ошибки или перезапуска.
- Для восстановления состояния сохранять его до действия и применять по явной ветке.
- Добавлять регрессионный тест на полный сценарий, где дефект был замечен.

### Область применимости

- Windows desktop;
- Java / Spring;
- UI;
- состояние приложения;
- тестирование;
- любой программный проект.

### Потенциальный reusable lesson

1. Внешний процесс не обязан сохранять состояние, ожидаемое UI.
2. После EOF, reconnect или restart команда должна задавать состояние явно.
3. Тест lifecycle обязан включать повторный запуск, а не только первый happy path.

## Проблема: решение о resume жило отдельно от команды запуска

**Уверенность: высокая для симптома и внесённого исправления; средняя для полноты физической проверки.** Источник — release commit `f8c89d8`, его тесты и hardware checklist; ручная проверка resume на HDMI ещё `NOT TESTED`.

### Что происходило

После остановки повторный старт мог начать файл с начала без вопроса о сохранённой позиции. Кроме того, после выбора «Продолжить» или «С начала» было важно не показать тот же диалог повторно и не потерять намерение пользователя, пока ожидался запуск output или уже подготовленного плеера.

### Корневая причина

Предложение resume появлялось при выборе элемента плейлиста, но старт имел несколько независимых путей: старт output, загрузка в подготовленное окно и запуск playback. Они могли обойти или повторно вызвать решение. Выбор пользователя не был частью атомарного перехода «решение → конкретная команда старта».

### Что делали или пробовали

До версии 0.1.0 проект проверял persistence и UI отдельно, но реальный переход после stop оказался покрыт неполно. В `f8c89d8` добавлены:

- `resumeDecisions` для записи принятого решения по точному `MediaFingerprint`;
- `PendingStart` для сохранения того, какой запуск ожидает решения;
- проверка `requireResumeDecision` во всех путях старта;
- удаление resume entry при «С начала»;
- unit-тест, подтверждающий удаление сохранённой позиции и нулевую стартовую позицию.

### Рабочее решение

Команда старта сначала проходит единый gate resume. Если требуется выбор, service сохраняет отложенную команду и публикует снимок состояния для UI. `resolveResume` принимает решение на serial executor, меняет persistence и продолжает ровно сохранённую команду. Выбор «Продолжить» запоминается, а «С начала» удаляет запись, чтобы исключить повторный диалог.

### Почему решение сработало

Решение пользователя и продолжение сценария теперь принадлежат одному последовательному application service, а не FXML-контроллеру и нескольким независимым путям запуска. Это устраняет потерю намерения при асинхронном диалоге.

### Как можно было обнаружить проблему раньше

Нужны scenario-тесты на уровне application service: выбрать файл с resume, нажать Play после stop, выбрать «Продолжить» или «С начала», затем убедиться в единственном запуске и правильной позиции. Вручную такой сценарий должен идти отдельным пунктом acceptance checklist, а не считаться покрытым unit-тестом репозитория.

### Как предотвратить повторение

- Делать пользовательское решение частью state machine, а не побочным эффектом UI.
- Входить в один gate из всех путей, которые могут запустить один и тот же use case.
- Хранить точное отложенное действие, а не восстанавливать его по косвенным признакам.
- Проверять и выбор «нет», и выбор «да», и повторный запуск после них.

### Область применимости

- Java / Spring;
- UI;
- состояние приложения;
- работа с файлами;
- тестирование;
- любой программный проект.

### Потенциальный reusable lesson

1. Асинхронный пользовательский выбор должен продолжать конкретную отложенную команду.
2. Один бизнес-gate необходимо вызывать из всех entry point сценария.
3. Состояние принятого решения должно быть идемпотентным и привязанным к конкретной сущности.

## Общие уроки проекта

- Самые дорогие проблемы выявились не в чистой доменной логике, а на границах: драйвер Windows, named pipe mpv, topology дисплеев и неявное состояние внешнего процесса.
- Для операций, меняющих систему, нельзя считать precondition проверкой. Нужны snapshot, явное подтверждение, проверка результата, rollback и recovery journal.
- Временные представления ОС — GDI-имя, номер `mpv --screen`, active source — не заменяют стабильный идентификатор физического ресурса.
- Hardware smoke обнаружил то, чего не могли доказать unit-тесты: реальное поведение topology, clone и разницу 59,940/60 Гц. Эти проверки нужно оставлять отдельными и честно маркировать `NOT TESTED`, пока нет реального оборудования.
- Интеграция с внешним процессом требует собственной state machine: пауза, EOF, disconnect и fallback не должны зависеть от неявных defaults mpv.
- Короткая история полезна только там, где commit, ADR и тесты подтверждают один факт. Проекту стоит и дальше фиксировать отдельными commit исправления, найденные в hardware smoke, и их регрессионные тесты.
- Сборка app-image и EXE уже подтверждена, но чистая install/update/uninstall, GitHub Actions, physical HDMI audio, UI hot unplug/replug, Windows 11 и долгий прогон остаются `NOT TESTED`. Незакоммиченный переход к AppFleet/Inno Setup также нельзя считать завершённым до этих проверок.

## Кандидаты для будущих Skills

### Capability confidence and safe fallback

- Предполагаемое название Skill: `capability-confidence-fallback`.
- Какую проблему он предотвращает: ложную уверенность, когда часть системного API доступна, а часть — нет.
- Когда его следует использовать: при интеграции с ОС, драйверами, SDK, оборудованием или внешними сервисами с несколькими источниками данных.
- Основные правила: отдельно хранить достоверные и fallback-данные; присваивать уровень уверенности; не заполнять неизвестные поля догадками; запретить опасную автоматизацию при слабой идентификации; добавить проверки частичного отказа.
- Насколько он универсален: `general`.

### Windows asynchronous named-pipe protocol

- Предполагаемое название Skill: `windows-overlapped-named-pipe`.
- Какую проблему он предотвращает: зависание или потерю ответов при двунаправленном IPC с событиями.
- Когда его следует использовать: Java/JNA-клиент Windows named pipe одновременно посылает команды и принимает асинхронные события.
- Основные правила: один reader; request correlation; overlapped I/O; явное владение native memory и handles; timeouts, cancellation и disconnect; integration-тест с событиями между командами.
- Насколько он универсален: `technology-specific`.

### Recoverable operating-system mutation

- Предполагаемое название Skill: `recoverable-system-mutation`.
- Какую проблему он предотвращает: повреждённое или неизвестное состояние ОС после ошибки, отключения устройства или аварийного завершения.
- Когда его следует использовать: при временной смене display topology, режимов экрана, сетевых настроек, служб, файлов или иных пользовательских конфигураций.
- Основные правила: snapshot до первого изменения; явное согласие пользователя; validate → apply → read-back; rollback при любом mismatch; persistent recovery journal; не стирать журнал до подтверждённого восстановления.
- Насколько он универсален: `general`.

### External process lifecycle contract

- Предполагаемое название Skill: `external-process-lifecycle-state`.
- Какую проблему он предотвращает: расхождение UI и фактического состояния CLI-процесса после EOF, ошибки, reconnect или restart.
- Когда его следует использовать: при управлении медиаплеером, браузером, CLI, worker-процессом или локальным сервисом.
- Основные правила: state machine в приложении; явные команды состояния после каждой границы; отдельная ветка восстановления; process containment; тайм-ауты; тесты на повторную загрузку и аварийное завершение.
- Насколько он универсален: `general`.

### Deferred user-decision flow

- Предполагаемое название Skill: `deferred-user-decision-flow`.
- Какую проблему он предотвращает: потерю или двойное применение решения пользователя в асинхронном UI-сценарии.
- Когда его следует использовать: когда подтверждение, resume, permission, conflict resolution или выбор файла должен продолжить конкретную команду.
- Основные правила: единый business gate; immutable UI snapshot; сериализованный application service; точное pending action; идемпотентность выбора; сценарные тесты для каждого решения и повторного запуска.
- Насколько он универсален: `general`.

### Hardware evidence and release honesty

- Предполагаемое название Skill: `hardware-release-evidence`.
- Какую проблему он предотвращает: подмену аппаратной или установочной проверки успешной сборкой и mock-тестом.
- Когда его следует использовать: при релизе desktop, mobile, embedded или hardware-integrated приложения.
- Основные правила: разделять automated, integration и manual hardware tests; использовать только статусы `PASS`, `FAIL`, `NOT TESTED`, `BLOCKED`; не считать EXE проверенным без чистой установки; привязывать результат к среде и версии; не скрывать непройденные сценарии.
- Насколько он универсален: `general`.
