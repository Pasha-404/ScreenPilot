# ADR-0005: JavaFX получает снимки состояния, а вывод проверяется по физическому target

- Статус: `ACCEPTED`
- Дата: 2026-08-07 (уточнён 2026-09-17)

## Контекст

Этап 6 добавляет постоянное JavaFX-окно и соединяет уже проверенные адаптеры mpv и Windows в единый пользовательский сценарий. Контроллер не может самостоятельно хранить состояние сессии или выполнять Win32, IPC и файловые операции: это приведёт к гонкам между JavaFX Application Thread, `application-serial`, `mpv-ipc-reader` и `display-poller`.

Технический прототип размещал mpv на вручную подтверждённом номере `--screen=1`. Этот номер не является идентификатором физического экрана и не должен попадать в пользовательский интерфейс. В условиях нескольких экранов ошибочный вывод видео на встроенный дисплей недопустим.

## Рассмотренные варианты

1. Хранить изменяемое состояние и бизнес-логику в FXML-контроллере.
2. Дать контроллеру напрямую вызывать Windows и mpv-адаптеры из JavaFX Application Thread.
3. Создать application service с единственным последовательным состоянием; передавать в UI неизменяемые снимки; размещать окно mpv нативно по физическим координатам выбранного target и проверять фактические границы.

## Решение

Выбран вариант 3.

1. `ApplicationState` — неизменяемый снимок: экраны, выбранный target и режим, файл, состояние output/player, прогресс и пользовательское сообщение.
2. `ScreenPilotController` и FXML не содержат бизнес-правил. Они отправляют команды application service и отображают только опубликованный снимок на JavaFX Application Thread через `Platform.runLater`.
3. Все use cases, Win32, файловые операции и ожидание IPC сериализуются на `application-serial`. JavaFX-поток создаёт окно, открывает стандартные диалоги и применяет готовое состояние к controls.
4. Номер `mpv --screen` не используется в основном пользовательском пути: он не является Windows display identity, а JavaFX `Screen` имеет другую (масштабируемую) систему координат. После старта mpv Win32-адаптер на отдельном thread временно включает `PER_MONITOR_AWARE_V2`, находит окно по уникальному title **и PID** дочернего процесса, устанавливает его outer bounds ровно в `DisplayBounds` target через `SetWindowPos` и читает границы обратно. Несовпадение — ошибка запуска с закрытием mpv и rollback topology; вывода на встроенный экран как fallback нет.
5. При отключении выбранного target poller немедленно ставит `player.shutdown()` в отдельную аварийную очередь, не ожидая занятый application service. Затем service переводит output в ошибку, запускает rollback, обновляет список экранов и оставляет UI на встроенном дисплее доступным. Автовозобновления после повторного подключения нет.

## Последствия и риски

- UI остаётся отзывчивым, а состояния output и player не дублируются.
- JavaFX `Screen` не участвует в сопоставлении physical target с окном mpv. Отдельный Win32-адаптер работает с одним типом координат и отклоняет как окно на другом экране, так и логически масштабированные границы mixed-DPI.
- Job Object обязателен для рабочих и metadata-процессов mpv на Windows; ошибка его назначения останавливает запуск до открытия IPC.
- Ручные DPI, HDMI и hot-unplug-проверки остаются hardware-тестами; обычный `test` не меняет конфигурацию Windows.

## Проверки

Перед аппаратным запуском должны проходить unit-тесты состояния, native-layout, точных границ окна и UI bindings. Hardware smoke этапа 6 проверит: один файл, выбранный внешний target, stop/recovery, потерю HDMI, mixed DPI и отсутствие видео на встроенном экране.
