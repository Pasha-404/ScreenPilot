# ADR-0005: JavaFX получает снимки состояния, а вывод проверяется по физическому target

- Статус: `ACCEPTED`
- Дата: 2026-08-07

## Контекст

Этап 6 добавляет постоянное JavaFX-окно и соединяет уже проверенные адаптеры mpv и Windows в единый пользовательский сценарий. Контроллер не может самостоятельно хранить состояние сессии или выполнять Win32, IPC и файловые операции: это приведёт к гонкам между JavaFX Application Thread, `application-serial`, `mpv-ipc-reader` и `display-poller`.

Технический прототип размещал mpv на вручную подтверждённом номере `--screen=1`. Этот номер не является идентификатором физического экрана и не должен попадать в пользовательский интерфейс. В условиях нескольких экранов ошибочный вывод видео на встроенный дисплей недопустим.

## Рассмотренные варианты

1. Хранить изменяемое состояние и бизнес-логику в FXML-контроллере.
2. Дать контроллеру напрямую вызывать Windows и mpv-адаптеры из JavaFX Application Thread.
3. Создать application service с единственным последовательным состоянием; передавать в UI неизменяемые снимки; считать номер mpv-экрана лишь кандидатом и проверять фактическое окно по физическим координатам target.

## Решение

Выбран вариант 3.

1. `ApplicationState` — неизменяемый снимок: экраны, выбранный target и режим, файл, состояние output/player, прогресс и пользовательское сообщение.
2. `ScreenPilotController` и FXML не содержат бизнес-правил. Они отправляют команды application service и отображают только опубликованный снимок на JavaFX Application Thread через `Platform.runLater`.
3. Все use cases, Win32, файловые операции и ожидание IPC сериализуются на `application-serial`. JavaFX-поток создаёт окно, открывает стандартные диалоги и применяет готовое состояние к controls.
4. Для запуска mpv application service сопоставляет `DisplayBounds` выбранного физического target с доступными JavaFX `Screen` и получает кандидатный номер mpv. После запуска Win32-проверка обязана подтвердить, что центр окна mpv лежит в bounds выбранного target. При несовпадении mpv закрывается, а изменённая topology восстанавливается; вывода на встроенный экран как fallback нет.
5. При отключении выбранного target service переводит output в ошибку, останавливает mpv, обновляет список экранов и оставляет UI на встроенном дисплее доступным. Автовозобновления после повторного подключения нет.

## Последствия и риски

- UI остаётся отзывчивым, а состояния output и player не дублируются.
- Для безопасного размещения понадобится небольшой Win32-адаптер окна mpv и unit-тесты чистого сопоставления координат.
- JavaFX `Screen` не считается источником истины о physical target: окончательное решение принимает проверка Win32 по `DisplayBounds`.
- Ручные DPI и HDMI-проверки остаются hardware-тестами; обычный `test` не меняет конфигурацию Windows.

## Проверки

Перед аппаратным запуском должны проходить unit-тесты состояния, разрешения координат и UI bindings. Hardware smoke этапа 6 проверит: один файл, выбранный внешний target, stop/recovery, потерю HDMI и отсутствие видео на встроенном экране.
