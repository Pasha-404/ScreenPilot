# ScreenPilot: инструкции агенту-разработчику

## Главный источник требований

Перед изменением проекта полностью прочитай:

1. `ScreenPilot_TZ.md` — обязательное техническое задание и основной источник решений.
2. `ScreenPilot_FT.md` — исходные функциональные требования и дополнительный контекст.
3. `screen.png` — ориентир по компоновке, но не требование точного копирования.

При расхождении документов соблюдай `ScreenPilot_TZ.md`. Текущий прямой запрос пользователя имеет приоритет над файлами проекта.

Не редактируй `ScreenPilot_FT.md`, если пользователь прямо этого не попросил.

## Порядок разработки

Следуй этапам из раздела 29 `ScreenPilot_TZ.md` по порядку.

Первая работа в пустом репозитории:

1. Этап 0 — создать воспроизводимый Gradle-каркас, Wrapper, модули, version catalog, `.gitignore`, README и каталог ADR.
2. Этап 1 — сделать минимальный mpv/Windows-прототип и оформить `docs/adr/0001-video-engine.md`.

Не начинай полноценный JavaFX-интерфейс до решения gate из раздела 28.

Если обязательная аппаратная проверка невозможна без подключённого HDMI-экрана, выполни всю доступную реализацию и автоматическую проверку, затем пометь оставшиеся пункты `NOT TESTED`. Не выдавай mock-тест за проверку на реальном оборудовании.

После каждого этапа:

- запусти относящиеся к этапу тесты и сборку;
- исправь обнаруженные ошибки в пределах текущего этапа;
- обнови README и ADR, если изменились команды или решения;
- кратко перечисли готовое, результаты проверок и оставшиеся аппаратные проверки.

## Зафиксированная техническая база

- Windows 10/11 x64, минимальная проверяемая система — Windows 10 build 19045.
- Java 21 LTS.
- JavaFX 21.
- Gradle Wrapper и Kotlin DSL.
- JNA для Win32.
- Основной кандидат видеодвижка — поставляемый `mpv.exe`, управляемый через локальный JSON IPC named pipe.
- Установка через `jpackage` для текущего пользователя без прав администратора.

Точные версии библиотек фиксируй в `gradle/libs.versions.toml`. Не используй динамические версии и snapshot-зависимости.

Когда работа касается библиотеки, SDK, API, Gradle, JavaFX, JNA, mpv или Win32, сначала проверь актуальную официальную документацию. Для библиотек используй Context7 согласно доступным инструкциям проекта.

## Неподвижные границы MVP

- Видео выводится только на один выбранный внешний экран.
- На экране ноутбука нет preview, thumbnails или второго видеопотока.
- HDMI обязателен; другие внешние подключения поддерживаются без отдельной дорогостоящей логики.
- ScreenPilot не меняет системное аудиоустройство Windows по умолчанию.
- ScreenPilot не включает системный HDR автоматически.
- Для MVP обязателен HEVC Main 10 и корректный HDR→SDR tone mapping. Native HDR — P1 после успешного прототипа.
- Изменения дисплеев временные. Перед изменением сохраняй исходное состояние и реализуй rollback/recovery.
- Не меняй параметры встроенного экрана и не делай внешний экран primary.
- Обычная установка и работа не требуют прав администратора.
- Функции из раздела 31 ТЗ не добавляй в MVP.

## Правила безопасной реализации

- До изменения display topology сначала реализуй read-only обнаружение и тесты JNA layout.
- Любой display mode сначала проверяй, затем применяй временно и сверяй фактический результат.
- При ошибке не продолжай в неопределённом состоянии: останови вывод, сохрани диагностику и выполни rollback.
- Все Win32 handles, JNA callbacks, процессы, IPC-каналы и executors должны иметь явный lifecycle и закрытие.
- Не выполняй Win32, IPC и файловые операции на JavaFX Application Thread.
- Запускай mpv через `ProcessBuilder` со списком аргументов, без shell и ручной сборки командной строки.
- Не загружай пользовательские mpv-конфиги и скрипты.
- Не добавляй в репозиторий непроверенные бинарники. Для mpv зафиксируй источник, версию, SHA-256 и лицензии.
- Не добавляй сеть, телеметрию, токены или секреты.

## Архитектурная дисциплина

- Соблюдай границы модулей из раздела 7 ТЗ.
- `screenpilot-domain` не зависит от JavaFX, JNA, mpv, Jackson и файловой системы.
- UI не содержит бизнес-логику и не хранит независимую копию состояния.
- Алгоритм выбора режима, state machines, persistence и recovery покрывай unit-тестами.
- Аппаратные тесты отделяй тегом `hardware`; обычный `test` не должен менять конфигурацию Windows.
- Существенное изменение архитектуры оформляй ADR до реализации.

## Когда задавать вопрос пользователю

Сначала исследуй репозиторий, документацию и безопасные варианты самостоятельно.

Задай короткий конкретный вопрос, если решение:

- меняет границы MVP;
- требует платной зависимости, сертификата или внешнего сервиса;
- противоречит `ScreenPilot_TZ.md`;
- может изменить или повредить пользовательскую конфигурацию вне описанного rollback;
- требует выбора нового видеодвижка после неуспешного mpv gate.

Не останавливай работу из-за отсутствия второстепенной информации. Зафиксируй безопасное локальное решение в ADR и продолжай в пределах ТЗ.

## Критерий честного отчёта

Используй только следующие статусы:

- `PASS` — проверка действительно выполнена и прошла;
- `FAIL` — проверка выполнена и не прошла;
- `NOT TESTED` — нет оборудования, среды или проверки;
- `BLOCKED` — продолжение конкретного этапа невозможно без решения пользователя.

Не называй этап завершённым, если его P0-критерий имеет статус `FAIL` или `NOT TESTED`.
